4. THE --all-cases FLAG, EXPLAINED
----------------------------------
What it is: a new switch for the W3C test runner
(scripts\run_w3c_conformance.py). Without it, the runner does exactly what
it did before (1,727 run, 858 skipped), so Jenkins is not changed. With it,
the 858 "skipped" cases run in 4 extra "lanes", each judged fairly:

 Lane              | Cases | How it runs                        | What counts as a pass
 core (as before)  | 1,727 | Eiffel test program                | the W3C answer
 legacy-names      |   309 | Eiffel test program with the old   | the W3C answer (these tests
 (old editions)    |       | 4th-edition name rules ON          |  were written for those rules)
 external-entities |   247 | the new DLL program; loads the     | the W3C answer
                   |       | extra files like Expat programs do |
 optional-error    |    28 | normal program                     | ACCEPT or REJECT (the spec
                   |       |                                    |  allows both); crash = fail
 xml-1.1           |   274 | normal program                     | ACCEPT or REJECT (there is no
                   |       |                                    |  XML 1.0 answer); crash = fail

How to run it (PowerShell, from the w7-smoke folder):

  # 1. build the two DLLs (smoke test on)
  $env:ISE_C_COMPILER = "msc_vc140"
  .\scripts\build_native_eiffel.ps1
  .\scripts\build_native_eiffel.ps1 -BuildTier Assertions

  # 2. build the DLL test program, once per DLL (in a VS x64 prompt)
  cl /nologo /Iinclude tests\native\xpact_w3c_case.c build\native-eiffel\xpact.lib /Fe:build\w3c-dll\xpact_w3c_case.exe
  cl /nologo /Iinclude tests\native\xpact_w3c_case.c build\native-eiffel\xpact_assertions.lib /Fe:build\w3c-dll\xpact_w3c_case_assertions.exe
  copy build\native-eiffel\xpact.dll, build\native-eiffel\xpact_assertions.dll build\w3c-dll\

  # 3. build the two Eiffel test programs (as run_benchmarks.ps1 does)
  ec -batch -clean -finalize -config benchmarks\xpact_benchmarks.ecf -target xpact_benchmarks
  ec -batch -clean -finalize -keep -config benchmarks\xpact_benchmarks.ecf -target xpact_benchmarks_assertions
  (then finish_freezing in EIFGENs\<target>\F_code)

  # 4. run everything
  python scripts\run_w3c_conformance.py --all-cases --timeout 30 `
    --engine Finalized=EIFGENs\xpact_benchmarks\F_code\xpact_benchmarks.exe `
    --engine FinalizedAssertions=EIFGENs\xpact_benchmarks_assertions\F_code\xpact_benchmarks.exe `
    --entity-engine Finalized=build\w3c-dll\xpact_w3c_case.exe `
    --entity-engine FinalizedAssertions=build\w3c-dll\xpact_w3c_case_assertions.exe

  Shortcut: test-runs\2026-10-27-w3c-after-fixes\run-timeout-30s.ps1
  Reports: summary.md (has a table per lane), results.tsv (column "lane"),
  junit.xml (lane in the test class name).
  The same text is in docs\w3c-xml-conformance.md, section "All cases".


5. THE FIXES (one problem each; CLAUDE.md format, short)
--------------------------------------------------------
All: student PC, Windows 11, EiffelStudio 25.12.9.8922, MSVC 19.51,
msc_vc140, finalized builds with and without assertions.
Each one was checked with a tiny example first, then with the full run
(section 2) and the regression tests (section 6).

[x] F1  An entity that includes itself CRASHED the DLL
        Test: not-wf-ext-sa-001 (file 001.ent contains &e; itself)
        Expected: REJECT "recursive entity reference" (as Expat)
        Before: crash, stack overflow 0xC00000FD (assertions build: 0xC0000005)
        Cause (confirmed): the parent marked the entity "open" only AFTER
          the external file was read, and the child parser did not know
          which entities were open, so it never noticed the loop.
        Fix: src\xp_parser.e - mark the entity open BEFORE reading it; the
          child parser inherits the list of open entities and checks it.
        After: REJECT "recursive entity reference", both builds.

[x] F2  "%name;" INSIDE a declaration in an external DTD was rejected
        Example: an external DTD with  <!ENTITY % a "b|c">  <!ELEMENT h (%a;)*>
        Tests: 44 (+4 found after the first fix), among them the XML
          specification itself (pr-xml-*, spec.dtd line 318)
        Expected: ACCEPT (allowed in external DTDs, XML 1.0 section 2.8)
        Before: REJECT "invalid token" / "syntax error" / "unclosed token"
        Cause (confirmed): the parser never replaced %name; inside
          ELEMENT / ATTLIST / NOTATION declarations.
        Fix: src\xp_parser.e - in an external DTD, replace each %name;
          (outside quotes) by its text with one space before and after
          (spec 4.4.8). Also: the declaration may end inside the entity
          (tests invalid--005, -006, rmt-e2e-14), an entity may hold
          "INCLUDE[" of a conditional section (invalid-not-sa-022), and an
          external %name; inside a declaration is read like Expat does
          (valid-not-sa-003). In the INTERNAL DTD it stays an error, as
          the spec requires (checked).
        After: all 48 pass, both builds.

[x] F3  The ASSERTIONS DLL ended silently with 2 elements in an entity
        Example: entity file with  <e/><e/>  -> exit 0xC00000FF, no output
        Tests: valid-ext-sa-005, -006, ext01, ibm77n16, ibm77v04, ibm77v10
        Cause (confirmed): a class rule (invariant) says "at most 1 root
          element", but inside an external entity every top-level element
          was counted. With 2 the rule broke; only the assertions build
          checks it, and the error could not get back out through the DLL.
        Fix: src\xp_parser.e - count only the first top-level element.
        After: ACCEPT, both builds.

[x] F4  standalone="yes" + an entity declared only outside was ACCEPTED
        Tests: not-wf-sa03, ibm-not-wf-P32-ibm32n09, ibm-not-wf-P68-ibm68n06
        Expected: REJECT (rule "Entity Declared")
        Cause (confirmed): xpact did not remember WHERE an entity was declared.
        Fix: src\xp_parser.e - remember entities declared in the external
          DTD or in a parameter entity; in a standalone="yes" document a
          reference to one is an error. src\xp_native_parser.e - Expat code
          XML_ERROR_ENTITY_DECLARED_IN_PE (24).
        After: REJECT "entity declared in parameter entity", like Expat.

[x] F5  A text declaration without encoding="..." was ACCEPTED
        Tests: dtd07, encoding07 (file starts with <?xml version="1.0"?>)
        Expected: REJECT (at the top of an external file, encoding is required)
        Cause (confirmed): the check only required version OR encoding.
        Fix: src\xp_parser.e - in an external entity, encoding is required.
          Expat code XML_ERROR_TEXT_DECL (31).
        After: REJECT "text declaration not well-formed".

[x] F6a "<?xml ...?>" in the wrong place was ACCEPTED
        Test: not-wf-not-sa-002 (it comes from an internal %entity;)
        Expected: REJECT (only allowed at the very start of an external file)
        Fix: src\xp_parser.e - allowed only there; elsewhere the error
          "XML or text declaration not at start of entity" (Expat code 17).

[x] F6b An XML 1.0 document using an XML 1.1 entity was ACCEPTED
        Test: rmt-e2e-38 (the entity file says version="1.1")
        Expected: REJECT (W3C erratum E38)
        Fix: src\xp_parser.e - in an external entity only version 1.0.

[x] F7  The DLL gave the entity handler base = NULL
        Expat gives the base (folder) so programs can find relative files.
        Fix: src\xp_native_callback_handler.e - pass the parser's base
          (from XML_SetBase). The workaround in the test program now
          fires 0 times.
        Limitation: Expat passes the base where the entity was DECLARED;
          xpact now passes the base of the parser that reads the
          reference. Same in all W3C tests; not identical in every case.

[x] Error messages: new Expat error codes 24 and 31 added, so programs
    get the same error numbers as from Expat.

7. THE 28 "OPTIONAL ERROR" TESTS (you asked: what should they report?)
----------------------------------------------------------------------
What the suite says: TYPE="error". In the XML spec an "error" is a
mistake the parser MAY report or MAY ignore. So the official answer is
neither "not-wf" nor "invalid": it is "either answer is correct".
 - not-wf  = broken document -> MUST reject
 - invalid = breaks its own DTD rules -> only validating parsers check;
             xpact does not validate, so it accepts
 - error   = may reject, may accept   <- these 28

(27 earlier + x-rmt-008, which is also TYPE="error" but marked for
editions 1-4, so it was counted with the old-edition group before.)

What xpact answers (same in both builds; no crash, no timeout):
