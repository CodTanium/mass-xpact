## What changed
- 38a7ba9 Keep a second byte order mark after UTF-16 decoding (`src/xp_native_parser.e`, `src/xp_parser.e`)
- 8094783 Add the #158 report, update the plan and repair its table

The UTF-16 decoder removed the byte order mark, and `normalized_input` then removed a leading UTF-8 BOM from the already decoded text: a second U+FEFF, which is character data, was lost. The decoder now reports that it removed the mark, and `normalized_input` strips a leading mark only from unconverted UTF-8 input.

The same cause also made a **two-BOM UTF-16 document well-formed** (the second U+FEFF is text before the root); Expat rejects it, and now xpact does too.
