2. XPACT-CORE FINDINGS (only in Xpact-core, not in xpact)
--------------------------------------------------------
Environment: student PC, Windows 11, EiffelStudio 25.12.9.8922,
MSVC 19.51; Xpact-core 6c017fb5b6e04fd0ae401bc54bb3c6a3c3bd6676;
finalized, assertions on and off (same result).
Command: .\scripts\run_dual_regression.ps1 -Offline

Finding 1 - empty final call is rejected (14 runs)
  Expected: ACCEPT (xpact accepts; Expat 2.8.1 accepts, #121)
  Actual:   REJECT, "status 0, code 3: No element found", for every
            valid document without a CR, chunking "bytes".
            Same inputs pass when the last byte itself is final.
  Example:  "<root/>" as "<","r","o","o","t","/",">" non-final,
            then "" final.

Finding 2 - lone-CR chunk gives "error" with no error code (8 + 1 runs)
  Expected: ACCEPT (the cr-* inputs pass whole); and in any case an
            error code on Status_error (postcondition
            error_code_set_on_error).
  Actual:   8 runs "status 0, code 0" (cr-crlf, cr-lone, cr-attribute
            in "bytes" and "bytes-final"; cr-last-byte split after
            "<r/>"); 1 run "No element found" when the CR is the
            final chunk.
  Example:  "<r/>" non-final, then "\r" final -> REJECT, code 0.

Cause of 1 and 2: SUSPECTED (from reading the code, NOT traced).
  XT_XML_PARSER_BASE.parse only calls parse_buffer when
  utf_8_copied_count > 0. An empty chunk, or a lone CR that the codec
  holds back waiting for a possible LF, gives no bytes, so parse
  returns its default 0 (= Status_error) without parsing the buffered
  rest. The postcondition is not checked because the library's own
  assertions are off.
Fix: none. Xpact-core is the pinned upstream parser; not changed.
