5. WHAT "36 MILLION PARSE CALLS" MEANS
--------------------------------------
A parse call is one time a program hands bytes to the parser ("here's the next
piece of XML"). 18.4 million went to xpact, and the same inputs (17.7 million
calls) went to Expat, so the results can be compared.

About 32 million of them come from one test: every W3C file fed byte by byte
and split at every position. A 1,000-byte file fed byte by byte alone is 1,000
calls.

Is it a good metric? Only partly. It measures HOW MUCH testing was done, not
HOW GOOD it was.

  Why it matters                                 Why it's weak
  - none of the 18 million xpact calls crashed   - inflated by byte-by-byte mode: many calls
  - shows broad, automated testing                 are tiny variations of the same file
  - caught a real bug only seen when input       - a big number doesn't mean the important
    arrives in pieces (#165)                       cases were tested
                                                 - says nothing about code coverage

Better numbers to lead with:
  Different documents tested   ~2.3 million    real variety, not repeats
  W3C tests passed             2,585 / 2,585   the official standard
  Bugs found and fixed         15              the testing worked
  Crashes                      0               stability
  Matches Expat                4,308 / 4,308   compatibility

How to say it: "In total about 36 million parse calls, mostly from feeding
every W3C file in every possible split, with 0 crashes."

7. IS XPACT INCREMENTAL NOW?
----------------------------
Short answer: the supervisor has built an incremental parser, but in a
different project. The xpact DLL we test (main @ 2488f44) still re-reads the
whole buffer on every call.

  Where                                 Incremental?   Evidence
  Xpact-core (andersoxie/Xpact-core)    YES            README: "A pure Eiffel, incremental,
  separate repo                                        libexpat-compatible XML parsing core ...
                                                       partial-token carryover across chunk
                                                       boundaries, buffer compaction and growth."
                                                       Last commit 15 Oct.
  xpact main (the DLL we test)          NO             src/xp_native_parser.e:917 still calls
                                                       handler.prepare_callback_replay
                                                       (delivered_callback_count): re-parse
                                                       everything, skip callbacks already delivered.
  XP_INCREMENTAL_PARSE_SESSION          STARTED, NOT   Added by the supervisor in June. Its doc:
  (prototype inside xpact)              CONNECTED      "It is not wired into XP_NATIVE_PARSER yet."
                                                       Handles only tags, attributes and text.

This week's measurements back this up: test 2 took ~25 minutes per build
because of the quadratic re-reading (F05-1), and bug #165 only existed
because of the replay design.

How the pieces fit:
- xpact = the parser behind the Expat-compatible DLL; all W3C, Expat and DLL
  tests run on it.
- Xpact-core = the supervisor's Eiffel rewrite of Expat; it streams properly.
  The dual regression lane (910/910) already runs it next to xpact, but it is
  not the code behind xpact.dll.

Questions for the supervisor:
  1. Did you mean Xpact-core? Will it replace the xpact parser behind the DLL,
     or should the June prototype be finished inside xpact?
  2. Should F05-1 (quadratic streaming, 10 MB limit) wait for that, rather than
     being fixed in the current replay design?

Possible proof: time Xpact-core with the same byte-by-byte feeding. If it is
really incremental, it should take seconds where xpact takes minutes.
(Not done yet.)


8. IF SOMEONE ASKS "WHAT'S NEXT?"
---------------------------------
- F02-2: when a whole document has an error, xpact reports no events before
  the error, while Expat does. This explains most of the 147 remaining
  differences in the in-pieces test.
- F05-1: the parser re-reads the whole buffer on every call. That's why the
  byte-by-byte test takes 25 minutes and why there is a 10 MB limit.
  Incremental parsing would fix it (see section 7).
- Jenkins: waiting for the official CI run before the open issues
  (#142, #146, #148, #151, #153, #154-#159, #165) are closed.
- PR #166 (#165): waiting for merge OK.
